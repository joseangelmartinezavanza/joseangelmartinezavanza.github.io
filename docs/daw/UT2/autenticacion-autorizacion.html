5. Autenticación y autorización

Hasta ahora hemos configurado qué sitios publica Apache y cómo responde a distintas peticiones. El siguiente paso es controlar quién puede acceder a determinados recursos.

Para hacerlo debemos distinguir dos procesos:

  • Autenticación: comprobar quién es el usuario.
  • Autorización: decidir si ese usuario, equipo o grupo puede acceder al recurso solicitado.
Idea clave

Autenticar y autorizar no son lo mismo.

Podemos resumirlo así:

¿Quién eres? → autenticación

¿Puedes entrar? → autorización

Apache combina ambos mecanismos mediante módulos y directivas de configuración.

Recorrido del apartado

Durante este apartado seguiremos este recorrido:

zona privada → autenticamos un usuario → decidimos quién puede entrar → trabajamos con grupos → combinamos condiciones → comparamos Basic y Digest

5.1. Qué vamos a proteger​

Continuaremos trabajando con el sitio empresa1 creado anteriormente.

Crearemos dentro de él una zona privada:

sudo mkdir -p /var/www/empresa1/privado

Creamos una página sencilla:

sudo nano /var/www/empresa1/privado/index.html

Por ejemplo:

<h1>Zona privada</h1>
<p>Solo deben acceder los usuarios autorizados.</p>

Antes de configurar ninguna restricción podemos comprobar que el recurso es accesible desde:

http://www.empresa1.test/privado/

Nuestro objetivo será conseguir que Apache no entregue ese contenido hasta que se cumplan las condiciones de acceso que indiquemos.

5.2. Autenticación Basic​

La autenticación Basic es uno de los mecanismos más sencillos que podemos utilizar en Apache.

Cuando un cliente intenta acceder a un recurso protegido:

  1. Apache responde indicando que necesita autenticación.
  2. El navegador solicita un nombre de usuario y una contraseña.
  3. El navegador vuelve a realizar la petición enviando las credenciales.
  4. Apache comprueba si son válidas.
  5. Después se aplica la autorización correspondiente.

Apache utiliza para este mecanismo el módulo:

mod_auth_basic

y, en este caso, utilizaremos el proveedor de autenticación basado en fichero.

Basic no cifra las credenciales

En HTTP Basic el usuario y la contraseña se codifican para enviarse en la cabecera HTTP, pero no quedan protegidos mediante cifrado.

Por eso no debemos considerar Basic seguro sobre una conexión HTTP sin cifrar.

Más adelante configuraremos HTTPS. La combinación habitual es:

autenticación Basic + HTTPS

De esta forma TLS protege tanto las credenciales como el resto de la comunicación.

Crear el archivo de usuarios​

Los archivos con credenciales no deben almacenarse dentro del directorio publicado por el servidor web.

Crearemos un directorio específico:

sudo mkdir -p /etc/apache2/auth

Para gestionar usuarios de autenticación Basic utilizamos:

htpasswd

Si el comando no estuviera disponible:

sudo apt install apache2-utils

Creamos el archivo y el primer usuario:

sudo htpasswd -cB /etc/apache2/auth/usuarios juan

El programa nos pedirá la contraseña sin mostrarla en pantalla.

en este ejemplo

-c crea el archivo de usuarios.

Debemos utilizar -c solo la primera vez. Si lo utilizamos sobre un archivo existente, podemos sobrescribirlo.

-B indica que la contraseña se almacenará utilizando bcrypt.

El archivo contiene el nombre del usuario y una representación hash de su contraseña, no la contraseña escrita directamente.

Para añadir otro usuario no utilizamos -c:

sudo htpasswd -B /etc/apache2/auth/usuarios maria

Podemos comprobar que existen entradas:

sudo cat /etc/apache2/auth/usuarios

No veremos las contraseñas originales.

Proteger el directorio​

Abrimos la configuración de empresa1:

sudo nano /etc/apache2/sites-available/empresa1.conf

Dentro del VirtualHost añadimos:

<Directory /var/www/empresa1/privado>
    AuthType Basic
    AuthName "Zona privada"
    AuthUserFile /etc/apache2/auth/usuarios
    Require valid-user
</Directory>

Las directivas cumplen funciones diferentes:

DirectivaFunción
AuthType BasicIndica el tipo de autenticación.
AuthNameDefine el nombre de la zona protegida que verá el cliente.
AuthUserFileIndica dónde está el archivo de usuarios.
Require valid-userPermite entrar a cualquier usuario válido del archivo.

Comprobamos:

sudo apache2ctl configtest

Y recargamos:

sudo systemctl reload apache2

Accedemos de nuevo a:

http://www.empresa1.test/privado/

El navegador debería solicitar usuario y contraseña.

Los usuarios no son usuarios de Debian

Los usuarios creados mediante htpasswd son usuarios utilizados por Apache para esta autenticación.

No estamos creando cuentas del sistema operativo con useradd ni permitiendo iniciar sesión en Debian.

5.3. Autenticación y autorización de usuarios​

Hasta ahora hemos utilizado:

Require valid-user

Esto significa:

puede acceder cualquier usuario que se autentique correctamente.

También podemos limitar el acceso a usuarios concretos.

Por ejemplo:

Require user juan

Solo permitirá acceder a juan, aunque existan otros usuarios válidos en el archivo.

También podemos indicar varios:

Require user juan maria

Aquí se ve claramente la diferencia:

  • AuthUserFile participa en la autenticación: permite comprobar las credenciales.
  • Require establece la autorización: decide quién puede acceder después de identificarse.

5.4. Trabajar con grupos de usuarios​

Cuando aumenta el número de usuarios resulta más cómodo autorizar grupos que escribir una lista de usuarios en cada configuración.

Crearemos:

sudo nano /etc/apache2/auth/grupos

Por ejemplo:

admins: juan maria

Cada línea relaciona un grupo con los usuarios que pertenecen a él:

nombre_grupo: usuario1 usuario2 usuario3

Para utilizar el archivo de grupos necesitamos la funcionalidad de:

mod_authz_groupfile

Podemos comprobar si está cargado:

sudo apache2ctl -M | grep authz_groupfile

Si no aparece, lo habilitamos:

sudo a2enmod authz_groupfile
sudo apache2ctl configtest
sudo systemctl reload apache2

Ahora podemos configurar:

/etc/apache2/sites-available/empresa1.conf
<Directory /var/www/empresa1/privado>
    AuthType Basic
    AuthName "Zona privada"
    AuthUserFile /etc/apache2/auth/usuarios
    AuthGroupFile /etc/apache2/auth/grupos
    Require group admins
</Directory>
en este ejemplo

AuthGroupFile indica dónde se encuentra el fichero que relaciona grupos y usuarios.

Require group admins autoriza únicamente a los usuarios que pertenecen al grupo admins.

El fichero de grupos, igual que el fichero de contraseñas, debe mantenerse fuera del árbol publicado por el servidor web.

Cambiar usuarios no exige recargar Apache

Si únicamente añadimos o modificamos usuarios en el archivo gestionado por htpasswd, o modificamos la composición del fichero de grupos, no estamos cambiando la sintaxis del archivo .conf.

Cuando modificamos la configuración de Apache, sí debemos seguir nuestro procedimiento habitual:

editar → configtest → recargar → comprobar

5.5. Autorización con Require​

La directiva Require permite decidir quién puede acceder a un recurso.

Durante esta unidad nos centraremos en las directivas que utilizaremos en nuestras prácticas:

DirectivaPermite el acceso a...
Require all grantedTodo el mundo.
Require all deniedNadie.
Require valid-userCualquier usuario autenticado correctamente.
Require user juan mariaLos usuarios indicados.
Require group adminsLos usuarios pertenecientes al grupo indicado.
Require ip 192.168.1.0/24Clientes cuya dirección IP pertenezca a esa red.
Alcance de este apartado

También existen directivas como Require host o Require local, pero no las necesitaremos para las prácticas principales de esta unidad. Las dejamos como referencia para consultar la documentación de Apache cuando sea necesario.

Restringir por dirección IP​

Podemos proteger un directorio sin pedir usuario y contraseña.

Por ejemplo:

/etc/apache2/sites-available/empresa1.conf
<Directory /var/www/empresa1/privado>
    Require ip 192.168.1.0/24
</Directory>

En este caso la decisión se toma según la dirección IP del cliente.

Combinar condiciones​

Apache permite combinar reglas mediante:

  • <RequireAll>: todas las condiciones deben permitir el acceso.
  • <RequireAny>: basta con que una de las condiciones permita el acceso.

En nuestras prácticas utilizaremos principalmente estos dos mecanismos. <RequireNone> y las condiciones negadas las veremos únicamente como ampliación.

Por ejemplo, queremos que juan pueda entrar solo si además accede desde nuestra red local:

/etc/apache2/sites-available/empresa1.conf
<Directory /var/www/empresa1/privado>
    AuthType Basic
    AuthName "Zona privada"
    AuthUserFile /etc/apache2/auth/usuarios

    <RequireAll>
        Require user juan
        Require ip 192.168.1.0/24
    </RequireAll>
</Directory>

Otro ejemplo: dentro del mismo bloque <Directory>, permitimos el acceso a juan o maria:

/etc/apache2/sites-vailable/empresa1.conf
<RequireAny>
    Require user juan
    Require user maria
</RequireAny>
Ampliación: condiciones negadas

Una condición negada no debe utilizarse sola para conceder acceso. Si queremos permitir a todos excepto a una red concreta, podemos utilizar una combinación como:

/etc/apache2/sites-available/empresa1.conf
<RequireAll>
    Require all granted
    Require not ip 192.168.1.0/24
</RequireAll>

Así existe una condición positiva que permite el acceso y otra que excluye el caso no deseado.

Esta configuración es útil para conocer las posibilidades de Require, pero no forma parte de las prácticas principales de la unidad.

Idea clave

En Apache 2.4 utilizaremos Require y sus mecanismos de combinación para expresar las reglas de autorización.

No necesitamos utilizar las directivas antiguas Order, Allow y Deny en las nuevas configuraciones de esta unidad.

5.6. Autenticación Digest​

Apache también dispone de autenticación Digest mediante:

mod_auth_digest

La estudiaremos para conocer otro mecanismo de autenticación y poder compararlo con Basic. No será una práctica principal de la unidad.

Ampliación: configurar Digest

Si queremos practicar su configuración, podemos habilitar el módulo:

sudo a2enmod auth_digest
sudo apache2ctl configtest
sudo systemctl reload apache2

Digest utiliza la herramienta:

htdigest

Para crear el archivo:

sudo htdigest -c /etc/apache2/auth/usuarios-digest "Zona privada" juan

La opción -c solo se utiliza la primera vez, porque crea el archivo. Para añadir otro usuario debemos omitirla:

sudo htdigest /etc/apache2/auth/usuarios-digest "Zona privada" maria

El nombre de zona utilizado al crear el usuario debe coincidir con AuthName.

Configuramos:

/etc/apache2/sites-available/empresa1.conf
<Directory /var/www/empresa1/privado>
    AuthType Digest
    AuthName "Zona privada"
    AuthUserFile /etc/apache2/auth/usuarios-digest
    Require valid-user
</Directory>

Comprobamos y recargamos:

sudo apache2ctl configtest
sudo systemctl reload apache2

Basic y Digest​

BasicDigest
Módulo principalmod_auth_basicmod_auth_digest
Herramienta para fichero de usuarioshtpasswdhtdigest
AuthTypeBasicDigest
Necesita AuthNameSí.Sí; además forma parte del realm utilizado por Digest.

Idea clave

Digest y Basic son mecanismos de autenticación diferentes, pero ninguno sustituye a HTTPS para proteger toda la comunicación.

Por eso debemos conocer Digest y saber diferenciarlo de Basic, pero la configuración completa queda como ampliación. Cuando lleguemos al apartado de HTTPS veremos la solución que protege toda la conexión.

5.7. Otros proveedores de autenticación​

Los usuarios no tienen por qué almacenarse siempre en un archivo local.

Apache puede trabajar con distintos proveedores de autenticación. Por ejemplo, puede integrarse con servicios de directorio como LDAP mediante los módulos correspondientes.

Alcance de la unidad

Debemos conocer que existen otras fuentes de usuarios. En las prácticas principales de este apartado trabajaremos con:

  • Archivos de usuarios.
  • Autenticación Basic.
  • Usuarios y grupos.
  • Reglas de autorización mediante Require.

La autenticación Digest se mantiene como ampliación porque forma parte de los mecanismos estudiados en los materiales de referencia. No configuraremos un servidor LDAP en esta unidad.

5.8. Qué ocurre cuando intentamos acceder​

Podemos resumir el proceso que acabamos de configurar:

  1. El cliente solicita un recurso protegido.
  2. Apache comprueba las reglas configuradas para ese recurso.
  3. Si se necesita identificar al usuario, inicia el proceso de autenticación.
  4. El navegador solicita las credenciales.
  5. Apache comprueba las credenciales mediante el proveedor configurado.
  6. Require determina si ese usuario o cliente está autorizado.
  7. Apache entrega el recurso o rechaza el acceso.

Durante estas pruebas podemos encontrarnos especialmente con dos códigos HTTP:

CódigoQué nos indica normalmente
401 UnauthorizedSe necesita autenticación o la autenticación no se ha completado correctamente.
403 ForbiddenApache entiende la petición, pero el acceso al recurso está prohibido.
No significan exactamente lo mismo

Un 401 nos orienta hacia un problema relacionado con la autenticación.

Un 403 nos hace revisar principalmente la autorización, las reglas Require, los permisos del sistema de archivos o las restricciones configuradas sobre el recurso. En Apache, según la configuración, un fallo de autorización después de una autenticación correcta también puede producir una respuesta 401, por lo que el código debe interpretarse junto con la configuración.

Para diagnosticar un problema

Si no podemos entrar en una zona protegida, no debemos asumir inmediatamente que la contraseña es incorrecta.

Debemos distinguir:

  • ¿Apache reconoce las directivas?
  • ¿Está cargado el módulo necesario?
  • ¿Puede leer el archivo de usuarios?
  • ¿Las credenciales son correctas?
  • ¿El usuario está autorizado por Require?
  • ¿La regla por IP o grupo permite el acceso?

Separar autenticación de autorización ayuda mucho a localizar el problema.

5.9. Para comprobar que lo has entendido​

Antes de continuar

Comprueba que puedes:

  1. Diferenciar autenticación y autorización.
  2. Explicar para qué sirve AuthType.
  3. Explicar para qué sirven AuthName y AuthUserFile.
  4. Crear un archivo de usuarios mediante htpasswd.
  5. Explicar por qué -c solo debe utilizarse al crear el archivo.
  6. Proteger un directorio con autenticación Basic.
  7. Diferenciar Require valid-user de Require user.
  8. Crear un fichero de grupos y utilizar AuthGroupFile.
  9. Autorizar un grupo mediante Require group.
  10. Restringir el acceso mediante una dirección IP.
  11. Combinar condiciones con <RequireAll> y <RequireAny>.
  12. Explicar por qué Basic debe utilizarse sobre HTTPS.
  13. Identificar las diferencias principales entre Basic y Digest.
  14. Diferenciar de forma básica un error 401 Unauthorized de un 403 Forbidden.
  15. Relacionar estas configuraciones con los módulos de Apache que las proporcionan.
