8. Contenidos y tipos MIME

Hasta ahora hemos configurado Apache para publicar distintos sitios, controlar el acceso y proteger las comunicaciones. Ahora vamos a centrarnos en qué tipo de contenido entrega Apache y cómo informa al navegador sobre ese contenido.

En esta parte diferenciaremos entre contenido estático y dinámico y veremos el papel de los tipos MIME en las respuestas HTTP.

Idea clave

Apache no solo entrega páginas HTML. Puede servir hojas de estilo, JavaScript, imágenes, vídeos, documentos y otros recursos.

Para que el navegador sepa cómo debe interpretar cada recurso, la respuesta HTTP incluye un encabezado Content-Type cuyo valor utiliza un tipo MIME.

Recorrido del apartado

entendemos contenido estático y dinámico → vemos cómo Apache sirve archivos → entendemos los tipos MIME → comprobamos Content-Type → configuramos un tipo MIME cuando sea necesario

Sobre las comprobaciones de esta unidad

En el apartado anterior vimos que la redirección de HTTP a HTTPS es una configuración adicional. Las comprobaciones de esta sección utilizan las URL HTTP mostradas en los ejemplos.

Si has activado la redirección de forma permanente, realiza estas comprobaciones sobre el VirtualHost HTTPS o desactiva temporalmente la redirección durante la práctica. Lo importante es que la petición llegue al recurso que estamos comprobando.

8.1. Contenido estático​

Hablamos de contenido estático cuando el servidor puede entregar un recurso que ya existe en el sistema de archivos sin tener que generar su contenido específicamente para esa petición.

En esta unidad también nos interesa distinguir cómo se genera la respuesta de lo que ocurre después en el navegador. Un archivo JavaScript o CSS puede ser un recurso estático porque Apache lo entrega directamente, aunque el código pueda producir posteriormente un comportamiento dinámico en el navegador.

Algunos ejemplos son:

  • documentos HTML.
  • hojas de estilo CSS.
  • archivos JavaScript.
  • imágenes.
  • vídeos.
  • documentos descargables.

Por ejemplo, si tenemos:

/var/www/empresa1/
├── index.html
├── estilos.css
└── imagenes/
    └── logo.png

Apache puede localizar estos recursos y entregarlos al navegador cuando se solicitan.

No significa que el archivo nunca cambie

Una página puede actualizarse cada cierto tiempo y seguir considerándose contenido estático.

Lo importante es cómo se genera la respuesta cuando se solicita el recurso: si Apache entrega un archivo que ya existe, estamos ante contenido estático.

En nuestro laboratorio, la mayor parte del contenido que hemos utilizado hasta ahora es estático: las páginas index.html, los archivos CSS y las imágenes del sitio.

Servir un archivo estático​

Podemos comprobarlo utilizando el sitio empresa1 que ya tenemos configurado.

Creamos un recurso sencillo:

sudo nano /var/www/empresa1/estado.html
en este ejemplo

Creamos estado.html directamente dentro del DocumentRoot del sitio.

No necesitamos modificar la configuración de Apache para servir un archivo HTML que se encuentre dentro de la ubicación publicada por el VirtualHost.

Introducimos, por ejemplo:

<h1>Servidor Apache funcionando</h1>
<p>Este recurso se sirve como contenido estático.</p>
en este ejemplo

El contenido del archivo ya existe antes de realizar la petición. Apache no necesita ejecutar una aplicación para construir esta respuesta.

Podemos solicitarlo desde el navegador:

http://www.empresa1.test/estado.html

La respuesta contiene el contenido que ya estaba almacenado en el servidor.

8.2. Contenido dinámico​

El contenido dinámico es aquel cuyo contenido o comportamiento depende de algún procesamiento o interacción que no consiste simplemente en entregar un archivo ya existente.

En un servidor web podemos distinguir entre contenido que ya existe como recurso y contenido que necesita ser procesado o generado antes de enviarse al cliente. En esta unidad nos interesa especialmente esta diferencia porque afecta directamente a la forma en que trabaja y se configura el servidor web.

El resultado puede depender, por ejemplo, de:

  • los datos recibidos en la petición.
  • la identidad del usuario.
  • información almacenada en una base de datos.
  • la lógica de una aplicación.
  • la fecha o la hora.
  • otras condiciones del servidor.

Un área privada que muestra información diferente para cada usuario es un ejemplo de contenido dinámico.

Servidor web y aplicación

Apache puede participar en el funcionamiento de una aplicación dinámica, pero no debemos asumir que Apache por sí solo ejecuta cualquier lenguaje de programación.

Dependiendo de la arquitectura, el procesamiento puede realizarlo un módulo, un intérprete, un servidor de aplicaciones u otro servicio al que Apache transfiera la petición.

En esta unidad no vamos a instalar ni configurar un lenguaje de programación del lado servidor. Nos interesa comprender la diferencia entre entregar un recurso existente y generar una respuesta mediante procesamiento.

Comparación​

Contenido estáticoContenido dinámico
El recurso ya existe en el servidor.La respuesta se genera o modifica mediante procesamiento.
Apache puede entregarlo directamente.Interviene algún componente adicional de procesamiento.
Ejemplos: HTML, CSS, imágenes, archivos descargables.Ejemplos: una página personalizada para un usuario o una consulta a una base de datos.
La configuración del servidor suele ser más sencilla.La configuración puede requerir más componentes.
Coste y complejidad

El contenido dinámico suele requerir más recursos que la simple entrega de archivos estáticos, porque puede implicar procesamiento adicional y, en algunos casos, acceso a otros servicios.

También puede aumentar la complejidad de administración: cuantos más módulos, aplicaciones o servicios intervienen, más elementos debemos configurar, actualizar y mantener. Esto también puede ampliar la superficie que debemos controlar desde el punto de vista de la seguridad.

No confundamos el recurso estático con el comportamiento dinámico

Una página puede estar formada por archivos estáticos —HTML, CSS, JavaScript e imágenes— y, sin embargo, producir un comportamiento dinámico cuando JavaScript se ejecuta en el navegador.

Por eso conviene distinguir dos ideas:

  • Cómo se entrega un recurso: Apache puede entregar directamente un archivo que ya existe.
  • Qué ocurre después en el cliente o en el servidor: puede intervenir código que genere, modifique o procese el contenido o su comportamiento.

En esta unidad nos centraremos especialmente en el procesamiento que afecta a la configuración del servidor web.

8.3. ¿Qué es un tipo MIME?​

Cuando un navegador solicita un recurso, no basta con recibir una secuencia de bytes. También necesita saber qué tipo de contenido está recibiendo.

Para ello, el servidor incluye en la respuesta HTTP el encabezado:

Content-Type: text/html
en este ejemplo

Content-Type informa al cliente del tipo de contenido de la respuesta.

En este ejemplo, text/html indica que se trata de un documento HTML.

Los tipos MIME utilizan normalmente dos partes:

tipo/subtipo

Por ejemplo:

Tipo MIMESignificado
text/htmlDocumento HTML
text/cssHoja de estilos CSS
text/plainTexto plano
text/javascriptJavaScript
image/pngImagen PNG
image/jpegImagen JPEG
application/pdfDocumento PDF
video/mp4Vídeo MP4
Tipo MIME y extensión no son lo mismo

La extensión .html pertenece al nombre del archivo.

El tipo MIME text/html forma parte de la información de la comunicación HTTP.

Apache utiliza la extensión y su configuración para determinar qué tipo de contenido debe asociar a determinados recursos y, finalmente, enviar el Content-Type correspondiente.

8.4. MIME en la comunicación entre servidor, página y navegador​

En una comunicación web podemos encontrar información relacionada con los tipos MIME en distintos lugares:

  • Servidor web: informa del tipo de contenido mediante la cabecera Content-Type de la respuesta HTTP.
  • Cliente: puede indicar qué tipos de contenido acepta mediante la cabecera Accept.
  • Documento HTML: puede incluir información sobre el tipo de recurso en algunos elementos, aunque en muchos casos el atributo type no sea necesario.

Por ejemplo, una página puede enlazar una hoja de estilos indicando que se trata de CSS:

<link rel="stylesheet" href="estilos.css" type="text/css">
en este ejemplo

En HTML moderno el atributo type="text/css" no suele ser necesario para una hoja de estilos, pero nos sirve para identificar dónde aparece la información sobre el tipo de recurso en el propio documento.

El navegador también puede incluir una cabecera Accept en la petición, indicando los tipos de contenido que puede aceptar. Un ejemplo simplificado sería:

Accept: text/html, application/xhtml+xml, image/avif, image/webp, */*
en este ejemplo

Accept pertenece a la petición del cliente, mientras que Content-Type pertenece a la respuesta del servidor.

El valor */* significa que el cliente acepta cualquier tipo de contenido.

No necesitamos memorizar una lista concreta de valores de Accept. Lo importante es distinguir su función de la de Content-Type.

8.5. ¿Dónde aparece Content-Type?​

El encabezado Content-Type forma parte de las cabeceras HTTP de la respuesta.

Podemos comprobarlo sin modificar Apache utilizando curl desde la máquina que pueda acceder al sitio.

Comprobar que curl está disponible​

Antes de utilizarlo, comprobamos si curl está instalado:

curl --version

Si el sistema indica que la orden no existe, podemos instalarlo en Debian:

sudo apt update
sudo apt install curl

Una vez instalado, volvemos a comprobar:

curl --version
en este ejemplo

curl es una herramienta de línea de comandos que permite realizar peticiones a servicios como HTTP y consultar sus respuestas.

En esta unidad lo utilizaremos para observar las cabeceras HTTP que devuelve Apache, sin necesidad de descargar el contenido completo de la página.

Por ejemplo:

curl -I http://www.empresa1.test/estado.html
en este ejemplo

La opción -I solicita únicamente las cabeceras de la respuesta HTTP.

No necesitamos descargar el contenido completo para comprobar qué tipo MIME está enviando Apache.

Entre las cabeceras obtenidas deberíamos encontrar una línea similar a:

Content-Type: text/html
en este ejemplo

Apache ha identificado estado.html como HTML y ha informado al navegador mediante Content-Type: text/html.

El valor exacto puede incluir información adicional, como el conjunto de caracteres.

Comprobar otro tipo de recurso​

Creamos una hoja de estilos sencilla:

sudo nano /var/www/empresa1/prueba.css
en este ejemplo

El objetivo es comprobar que Apache no envía el mismo tipo MIME para todos los recursos, sino que relaciona determinadas extensiones con distintos tipos de contenido.

Introducimos:

body {
    font-family: sans-serif;
}
en este ejemplo

El contenido del archivo es CSS. Lo importante en esta comprobación no es el estilo aplicado, sino comprobar el tipo MIME que Apache asocia a la extensión .css.

Comprobamos las cabeceras:

curl -I http://www.empresa1.test/prueba.css
en este ejemplo

Ahora esperamos encontrar un Content-Type correspondiente a una hoja de estilos, normalmente text/css.

Podemos repetir la comprobación con una imagen u otro recurso que tengamos disponible.

8.6. ¿Cómo sabe Apache qué tipo MIME utilizar?​

Apache utiliza la configuración de tipos MIME proporcionada por el módulo mod_mime.

En Debian podemos consultar:

sudo cat /etc/apache2/mods-available/mime.conf

y la lista de tipos MIME del sistema se encuentra habitualmente en:

sudo cat /etc/mime.types
No necesitamos modificar estos archivos

Para los tipos habituales de HTML, CSS, JavaScript, imágenes o PDF, Apache ya dispone normalmente de las asociaciones necesarias.

En esta unidad nos interesa saber dónde se encuentran y cómo comprobarlas, no mantener manualmente una lista completa de tipos MIME.

8.7. Añadir un tipo MIME con AddType​

Puede ocurrir que tengamos un recurso con una extensión que Apache no asocie al tipo MIME que necesitamos.

En ese caso podemos utilizar la directiva:

AddType tipo-mime extensión

Por ejemplo:

AddType application/x-demo .demo
en este ejemplo

Esta directiva indica que los archivos cuya extensión sea .demo deben servirse utilizando el tipo MIME application/x-demo.

La directiva AddType pertenece a mod_mime.

Para realizar una prueba podemos crear un archivo:

sudo nano /var/www/empresa1/prueba.demo
en este ejemplo

El contenido del archivo no es lo importante en esta prueba. Queremos comprobar qué Content-Type envía Apache cuando encuentra la extensión .demo.

Por ejemplo:

Este es un archivo de prueba.
en este ejemplo

El archivo contiene texto, pero no vamos a dejar que Apache decida el tipo únicamente por el contenido. Vamos a asociar explícitamente la extensión .demo con application/x-demo.

Podemos añadir la directiva en el VirtualHost de empresa1:

etc/apache2/sites-available/empresa1.conf
<VirtualHost *:80>
    ServerName www.empresa1.test
    DocumentRoot /var/www/empresa1

    AddType application/x-demo .demo
</VirtualHost>
en este ejemplo

AddType puede utilizarse en la configuración del servidor, en un VirtualHost, en determinados contextos de directorio o mediante .htaccess cuando AllowOverride permite la categoría correspondiente.

En nuestro caso la colocamos en el VirtualHost porque estamos administrando directamente el servidor y estamos configurando un recurso estático.

Comprobamos la configuración y recargamos apache:

sudo apache2ctl configtest
sudo systemctl reload apache2

Y comprobamos la respuesta:

curl -I http://www.empresa1.test/prueba.demo
en este ejemplo

Ahora el encabezado Content-Type debería reflejar la asociación que acabamos de configurar:

Content-Type: application/x-demo

No debemos modificar mime.types para cada archivo

Los tipos MIME habituales ya están definidos en la configuración del sistema.

Solo necesitamos añadir una asociación cuando realmente tengamos un tipo o extensión que Apache no conozca o que necesitemos servir de una forma diferente.

Otras directivas

Apache dispone también de directivas como ForceType para forzar un tipo MIME en un contexto determinado.

No necesitamos utilizarla en nuestro laboratorio. Para nuestras configuraciones prácticas utilizaremos principalmente AddType cuando sea necesario asociar una extensión con un tipo MIME.

8.8. Relación entre extensión, tipo MIME y navegador​

Podemos resumir el proceso:

en este ejemplo

La extensión del archivo y la configuración de Apache permiten determinar el tipo de contenido. Apache lo comunica mediante Content-Type y el navegador utiliza esa información para interpretar la respuesta.

No debemos confundir este proceso con la ejecución de código del lado servidor.

Un archivo:

prueba.css

puede ser contenido estático y, al mismo tiempo, tener un tipo MIME:

text/css

El tipo MIME describe qué tipo de contenido se está entregando; no indica por sí mismo que el servidor tenga que ejecutar ese archivo.
